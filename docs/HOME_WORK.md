# ДЗ 2. От согласованного ТЗ к интерфейсу

## Задача

На семинаре вы провели интервью, составили ТЗ и согласовали его с заказчиком. Теперь по этому ТЗ нужно собрать и опубликовать страницу.

Работа строится так:

1. заказчик завершает и принимает ТЗ;
2. исполнитель собирает страницу на HTML и CSS;
3. исполнитель публикует результат и пишет отчет;
4. заказчик проверяет страницу;
5. исполнитель исправляет замечания, если они есть.

Оценивается не количество эффектов и блоков, а соответствие согласованному ТЗ, качество верстки и понимание собственного кода.

## Срок сдачи

**До воскресенья, 20.09.2026, 10:00 по московскому времени.**

К этому времени все PR по работе должны быть замержены, сайт опубликован, а пять итоговых ссылок отправлены преподавателю.

## Роли

Каждый студент продолжает работу в той же паре, что и на семинаре.

### Исполнитель

Вы делаете сайт по ТЗ, которое подготовили после интервью с заказчиком. Исполнитель отвечает за:

- HTML и CSS;
- выбор заготовок из конструктора;
- соответствие сайта ТЗ;
- публикация на GitHub Pages;
- отчет о реализации в пункте 4 исходного ТЗ;
- исправление замечаний заказчика.

### Заказчик

Вы завершаете согласование собственного ТЗ, а затем проверяете сайт, который сделал исполнитель. Заказчик отвечает за:

- точность фактов и разрешение на публикацию;
- проверка критериев готовности;
- конкретные замечания, если что-то сделано не по ТЗ;
- отзыв в пункте 5 исходного ТЗ;
- итоговое решение по работе.

## Что отправить преподавателю

Нужно отправить пять ссылок:

1. на замерженный PR с согласованным ТЗ;
2. на замерженный PR с реализацией;
3. на опубликованный сайт в GitHub Pages;
4. на замерженный PR с отчетом исполнителя в пункте 4 ТЗ;
5. на замерженный PR с отзывом заказчика в пункте 5 ТЗ.

## Общие правила

- Основной PR с кодом направляйте в `master` собственного форка, а не в репозиторий преподавателя.
- Используйте только HTML и CSS. JavaScript и сторонние CSS-библиотеки в этой работе не нужны.
- После начала работы пункты 1–3 ТЗ менять нельзя.
- `docs/TECH_TASK.md` хранит копию требований на момент начала работы. Отчет и отзыв добавляются в исходное ТЗ в репозитории с практикой.
- Используйте только те сведения, которые заказчик разрешил публиковать.
- Для страницы достаточно трех-пяти содержательных блоков. Не добавляйте секции ради количества.
- Удалите из итоговой версии все демонстрационные имена, тексты и ссылки.
- Вы должны понимать каждую строку своего HTML и CSS, включая код, взятый из конструктора.

## Если в ТЗ есть неясность

Не меняйте согласованное ТЗ под уже написанный сайт.

Если требование можно понять по-разному:

1. задайте заказчику конкретный вопрос в PR с исходным ТЗ;
2. получите ответ в комментарии;
3. добавьте ссылку на этот комментарий в описание PR с реализацией;
4. продолжайте работу с учетом ответа.

Сам текст пунктов 1–3 при этом не меняется. Комментарий заказчика служит уточнением.

## Как работать с конструктором

Выберите один из трех вариантов.

### Вариант 1. Взять готовый каркас

Подходит, если опыта пока немного.

1. Выберите один пример из `templates`.
2. Замените весь демонстрационный текст данными из ТЗ.
3. Удалите ненужные секции.
4. Замените или заметно переработайте хотя бы один блок.
5. Используйте примеры из `practice`, чтобы проверить верстку.

### Вариант 2. Изменить готовый каркас

Подходит большинству студентов.

1. Возьмите один пример из `templates` за основу.
2. Замените один или два блока вариантами из `blocks`.
3. Приведите все части к одной палитре, типографике и системе отступов.
4. Настройте адаптивность получившейся страницы.

### Вариант 3. Собрать страницу из блоков

Подходит тем, кто уверенно чувствует себя в HTML и CSS.

1. Соберите страницу из нескольких примеров из `blocks`.
2. Задайте общие CSS-переменные, контейнер и типографику.
3. Устраните конфликты классов и глобальных стилей.
4. Настройте адаптивную раскладку.

Выбор сложного варианта сам по себе не повышает оценку. Простая работа, точно сделанная по ТЗ, лучше сложной, но сломанной страницы.

## Порядок выполнения

### Этап 1. Получите согласованное ТЗ

Как исполнитель:

1. откройте PR с ТЗ в репозитории заказчика;
2. проверьте, что пункт 3 заполнен;
3. убедитесь, что заказчик написал `ТЗ СОГЛАСОВАНО`;
4. дождитесь, пока PR будет замержен;
5. сохраните ссылку на PR.

Как заказчик:

1. проверьте факты и список разрешенных сведений;
2. заполните свою часть проверки в пункте 3;
3. напишите `ТЗ СОГЛАСОВАНО` или попросите внести одно конкретное исправление;
4. после исправления замержите PR.

### Этап 2. Подготовьте репозиторий

1. Сделайте форк репозитория с домашней работой.
2. Клонируйте свой форк и откройте его в VS Code.
3. Создайте ветку `homework-2` от актуального `master`.
4. Скопируйте согласованное ТЗ в `docs/TECH_TASK.md`.
5. В начале файла добавьте ссылки на исходный файл и PR с согласованием.
6. Откройте `project/index.html` через Live Server.
7. Проверьте, что `project/styles.css` подключен относительным путем `styles.css`.
8. Настройте GitHub Pages с публикацией из ветки `master`.
9. Проверьте адрес страницы: он должен заканчиваться на `/project/`.

После этого локальная страница должна открываться, а в `docs/TECH_TASK.md` должна лежать согласованная версия ТЗ.

Рекомендуемый коммит: `chore: подготовить проект к работе`.

### Этап 3. Соберите HTML

Сначала займитесь содержанием и структурой, а не цветами.

На странице должны быть:

- первый экран с героем, темой и главной мыслью;
- блок с тремя обязательными фактами или этапами;
- завершение с итогом или главным действием;
- дополнительные блоки, только если они нужны по ТЗ.

Проверьте HTML:

- на странице ровно один `h1`;
- заголовки идут последовательно;
- элементы выбраны по смыслу;
- ссылка используется для перехода, а `button` — для действия на странице;
- повторяющийся компонент имеет понятные БЭМ-классы;
- нет пустых ссылок, случайных `id` и ненужных секций;
- демонстрационный текст удален.

Отключите CSS и прочитайте страницу. Ее содержание должно оставаться понятным.

Рекомендуемый коммит: `feat: добавить структуру и содержание страницы`.

### Этап 4. Добавьте стили

Обязательные требования:

- в проекте используется `box-sizing`;
- ширина содержимого ограничена контейнером или другим понятным способом;
- хотя бы одна линейная группа собрана через Flexbox;
- повторяющиеся элементы хотя бы в одном месте собраны через Grid;
- блоки используют общие цвета, шрифты и отступы;
- в CSS не осталось стилей от неиспользуемых частей конструктора.

В описании PR перечислите:

- какой вариант работы с конструктором вы выбрали;
- какие файлы из `templates`, `blocks` и `practice` использовали;
- что изменили в заимствованном коде.

Будьте готовы показать в своем CSS Flexbox, Grid и БЭМ и объяснить, зачем они используются.

Рекомендуемый коммит: `style: собрать оформление из готовых блоков`.

### Этап 5. Проверьте адаптивность

Проверьте страницу примерно на 360 px и 1200 px.

На обеих ширинах:

- нет горизонтальной прокрутки;
- блоки не перекрывают друг друга;
- текст не выходит за границы;
- строки не становятся слишком длинными;
- главная мысль и обязательные факты остаются заметны.

Также проверьте:

- все ссылки открываются;
- по интерактивным элементам можно пройти клавишей `Tab`;
- для фокуса есть заметное состояние `focus-visible`;
- текст и фон достаточно контрастны.

Рекомендуемый коммит: `fix: настроить адаптивность и состояния фокуса`.

### Этап 6. Сверьте результат с ТЗ

Откройте рядом `docs/TECH_TASK.md`, локальную страницу и версию на GitHub Pages.

Проверьте каждый критерий готовности. Для каждого пункта вы должны суметь показать конкретный элемент страницы. Отдельно убедитесь, что:

- первый экран передает тему и главную мысль;
- присутствуют три обязательных факта или этапа;
- пожелание заказчика учтено;
- запрещенных сведений нет;
- локальная и опубликованная версии совпадают.

Рекомендуемый коммит: `fix: привести страницу в соответствие с ТЗ`.

### Этап 7. Создайте PR с реализацией

1. Отправьте ветку `homework-2` в свой форк.
2. Создайте PR из `homework-2` в `master` своего форка.
3. Добавьте в описание PR:
   - ссылку на замерженный PR с ТЗ;
   - главную мысль страницы;
   - выбранный вариант работы с конструктором;
   - перечень использованных заготовок;
   - расположение Flexbox, Grid, БЭМ и медиазапроса;
   - результаты проверки на 360 px и 1200 px;
   - ссылку на GitHub Pages;
   - информацию об использовании ИИ.
4. Замержите PR в `master`.
5. Дождитесь обновления GitHub Pages и еще раз откройте сайт.
6. Добавьте заказчика в свой репозиторий.
7. Отправьте ему ссылки на репозиторий, PR и сайт.

### Этап 8. Заполните пункт 4 ТЗ

Вернитесь в репозиторий с практикой. Исполнитель должен отдельным PR добавить в исходное ТЗ раздел **«4. Отчет исполнителя о реализации»**.

В отчете укажите:

1. ссылку на исходное ТЗ;
2. ссылку на свой форк с домашней работой;
3. ссылку на замерженный PR с реализацией;
4. ссылку на сайт в GitHub Pages;
5. ссылку на конструктор;
6. выбранный вариант работы;
7. использованные заготовки;
8. таблицу соответствия требований и элементов страницы;
9. расположение Flexbox, Grid, БЭМ и медиазапроса;
10. результат проверки на 360 px и 1200 px;
11. информацию об использовании ИИ;
12. предусмотренный шаблоном статус `READY FOR CUSTOMER REVIEW`.

Не меняйте пункты 1–3. PR с пунктом 4 нужно замержить.

### Этап 9. Получите отзыв заказчика

После появления пункта 4 заказчик проверяет ТЗ и опубликованный сайт. Затем он отдельным PR добавляет раздел **«5. Отзыв заказчика»**.

В отзыве нужно указать:

1. верно ли переданы факты и смысл;
2. нет ли сведений, запрещенных к публикации;
3. выполнен ли каждый критерий готовности из ТЗ;
4. выполнены ли два критерия конкретной истории;
5. учтены ли пожелание и визуальное направление;
6. ссылки на PR с исправлениями, если они потребовались;
7. один из предусмотренных шаблоном итогов: `ACCEPTED` или `CHANGES REQUESTED`.

Фразы «все хорошо» недостаточно: из отзыва должно быть понятно, что именно проверил заказчик.

Если выбрано `CHANGES REQUESTED`, исполнитель исправляет замечания в отдельной ветке и отдельном PR. После обновления сайта заказчик повторяет проверку, меняет итог на `ACCEPTED` и замерживает PR с пунктом 5.

Если заказчик не отвечает, свяжитесь с ним заранее. Если это не помогло, до срока сдачи напишите преподавателю, чтобы получить другого проверяющего. Пустой пункт 5 без предварительной договоренности считается отсутствием отзыва.

### Этап 10. Завершите работу

1. Заполните чек-лист в конце этого файла.
2. При необходимости сделайте для чек-листа отдельный небольшой PR.
3. Добавьте в его описание ссылки на PR с пунктами 4 и 5.
4. Замержите все PR по работе.
5. Проверьте GitHub Pages, ссылки и отображение на 360 px и 1200 px.
6. Отправьте преподавателю пять итоговых ссылок.

## Оценивание

Максимум за работу — 10 баллов.

### Соответствие ТЗ — 2,5 балла

- работа начата после согласования ТЗ;
- первый экран передает тему и главную мысль;
- показаны три обязательных факта или этапа;
- учтены пожелания и ограничения;
- каждый критерий готовности можно проверить на странице.

### HTML — 1 балл

- один `h1` и правильный порядок заголовков;
- элементы выбраны по смыслу;
- повторяющиеся части имеют понятные БЭМ-классы;
- нет лишних секций и демонстрационного текста.

### CSS, Flexbox и Grid — 2 балла

- стили организованы понятно;
- Flexbox и Grid используются по назначению;
- выбранные блоки приведены к общей стилистике;
- отступы и типографика помогают читать страницу;
- студент может объяснить основные правила CSS.

### Адаптивность и доступность — 1,5 балла

- страница работает примерно на 360 px и 1200 px;
- нет горизонтальной прокрутки и наложения элементов;
- сайт можно использовать с клавиатуры;
- фокус заметен, ссылки работают.

### Работа с конструктором — 1 балл

- использованные материалы перечислены в PR;
- перенесен только нужный код;
- заготовки изменены под ТЗ;
- студент понимает перенесенный код.

### Репозиторий и публикация — 1 балл

- работа сделана в собственном форке;
- сайт находится в папке `project`;
- основной PR замержен в `master`;
- GitHub Pages открывает актуальную версию сайта;
- все ссылки приложены.

### Работа с заказчиком — 1 балл

- пункт 4 добавлен исполнителем отдельным PR;
- пункт 5 добавлен заказчиком отдельным PR;
- замечания исправлены;
- работа получила итог `ACCEPTED`;
- студент выполнил роль заказчика для своего партнера.

## Штрафы

Штрафы суммируются, но итоговая оценка не может быть ниже 0.

- **−1 балл**, если после первого коммита с домашней работой были изменены пункты 1–3 ТЗ. Уточнение в комментарии не считается изменением ТЗ.
- **−1 балл**, если нет отчета исполнителя в пункте 4 или PR с ним не замержен.
- **−1 балл**, если нет отзыва заказчика в пункте 5 или PR с ним не замержен.
- **−1 балл**, если сайт не опубликован на GitHub Pages.

## Когда за работу ставится 0 баллов

- Работа не сдана до указанного срока.
- Обнаружены признаки чужого кода, чужого текста или результата, созданного нейросетью.
- Студент не может ответить на вопросы по своему коду или принятым решениям.
- Итоговый чек-лист не заполнен.
- Хотя бы один PR по работе не замержен к моменту сдачи.
- Опубликованная страница не соответствует согласованному ТЗ.
- На странице опубликованы сведения, которые заказчик запретил публиковать.

Код из официального конструктора не считается чужим, если источник указан, выбранные части переделаны под ТЗ и студент может их объяснить.

## Использование ИИ

ИИ можно использовать как справочник или консультанта. Автором сдаваемой работы должен оставаться студент.

Можно:

- попросить объяснить конкретное свойство HTML или CSS;
- получить подсказку по одной ошибке;
- проверить свое понимание Flexbox, Grid, БЭМ или адаптивности;
- сверить уже готовую работу с критериями задания.

Нельзя:

- просить ИИ выполнить задание целиком;
- передавать ИИ ТЗ и просить готовые `index.html` и `styles.css`;
- поручать ИИ выбор и объединение блоков;
